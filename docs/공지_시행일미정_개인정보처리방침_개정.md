## 🔴 시행일 미확정 · Play 등록 → 도메인 이전 완료 후 7일 · 배포 금지

문안 안의 `[시행일 미정]` · `[공지일 미정]` 은 **자리표시자다.**
날짜를 넣기 전에는 아임웹에도 신규 사이트에도 올리지 않는다.

```
python3 scripts/check_placeholders.py    # 자리표시자가 남아 있으면 실패한다
```

### 9월 5일을 왜 철회했나

개정판은 제2조와 제5조에서 **수탁자를 Cloudflare, Inc. 로** 적는다. 그런데
`jinazen.com` 은 아직 아임웹이다(아래 실측). 이전이 끝나기 전에 시행하면
**사실보다 앞선 서술**이 된다.

이번 개정이 바로잡으려던 것이 정확히 그 종류의 오류였다 — 제3조가 「3개월」,
제5조 ④ 가 「위탁계약 종료 시까지」로 같은 데이터를 두고 다른 말을 하던 것.
**고치려는 것과 같은 오류를 새로 만들 수는 없다.**

> **새 시행일 = 도메인 이전 완료 + 7일** (사전 공지 기간)
> 날짜는 소유자가 이전 완료를 확인한 뒤에 넣는다.

### 언제가 되는가 — 사슬이 셋이다

```
D-U-N-S 발급  →  Play 스토어 등록  →  도메인 이전  →  +7일  →  시행
   대기 중            그 다음            그 다음
 (8/19 신청)
```

**도메인 이전은 Play 스토어 등록 뒤로 잡혀 있고, Play 등록은 D-U-N-S 를 기다린다.**
D-U-N-S 는 2026-08-19 에 신청해 아직 대기 중이다. 그래서 **방침 시행은 10월
이후**다.

앞의 두 칸이 언제 끝날지는 우리가 정하지 못한다. **정하지 못하는 것을 날짜로
적어 두면, 그 날짜가 지났을 때 방침이 거짓말을 시작한다.**

### ⚠ 「8/29 까지 공지」도 함께 무효다

8/29 는 9/5 에서 7일을 역산한 날짜였다. 시행일이 없어졌으므로 그 날짜도 없다.
**날짜 하나만 고치면 사전 공지 기간이 어긋난다** — 둘은 한 벌로 움직인다.

공지는 **이전 완료가 확정되는 날** 올리고, 그날부터 7일 뒤가 시행일이다.

## 🔴 먼저 확인할 것 — 어디에 올려야 하는가

**2026-08-27 실측: `jinazen.com` 은 아직 아임웹에서 서비스되고 있다.**

```
NS      ens1~4.hostcocoa.com        (아임웹 DNS)
A       3.171.185.13/54/61/121
server  nginx
쿠키    IMWEBVSSID · al=KR · _imweb_login_state
```

Cloudflare Pages 로 이전되지 않았고, 이 저장소의 신규 사이트는 **아직 배포되지
않았다.** 그래서 결론은 단순하다.

> **공지는 아임웹에 반드시 올라가야 한다.**
> 지금 손님이 보는 사이트가 그것 하나뿐이기 때문이다.

⚠ 시행일이 이전 완료 이후이므로, 공지를 올리는 시점에는 **아직 아임웹일
가능성이 높다.** 신규 사이트가 그때 떠 있으리라고 가정하지 않는다.

신규 사이트에도 같은 공지를 두었다(`privacy/notice/{,en/,ja/}`). 배포되는 즉시
같은 내용이 보이고, 이전 시점이 언제가 되든 공지가 끊기지 않는다.

**제안 — 둘 다 올린다.**

| 자리 | 무엇을 | 왜 |
|---|---|---|
| **아임웹 (필수)** | 아래 문안 3개 언어 + 개정 전문 | 공지일에 손님이 실제로 보는 곳 |
| 신규 사이트 (준비됨) | `privacy/notice/` 3개 언어 | 배포 후 자동으로 이어짐 |

⚠ **아임웹에는 「개정 전문」을 볼 자리도 함께 만들어야 한다.** 공지에서 신규
사이트 주소로 링크를 걸면, 배포 전에는 그 링크가 아무 데도 닿지 않는다.
아임웹 안에 페이지를 하나 더 만들어 개정 전문을 붙여 넣는 것이 확실하다
(전문은 `privacy/index.html` 의 본문 그대로).

## 🔴 날짜를 넣을 때 — 한 벌로 움직인다

이전 일정이 확정되면 아래를 **함께** 고친다. 하나라도 빠지면 문서끼리 다른
날짜를 말하게 된다.

| 자리 | 무엇 |
|---|---|
| `privacy/{,en/,ja/}index.html` | 문서 머리 · 제18조 ① |
| `privacy/notice/{,en/,ja/}index.html` | 공지일 · 시행일 · 본문 4곳씩 |
| 이 파일 | 제목 · 본문 · **파일명**(`공지_시행일미정_…`) |
| 각 파일 머리 주석 | 「시행일 미확정 … 배포 금지」 블록을 지운다 |

넣은 뒤 `python3 scripts/check_placeholders.py` 가 통과해야 배포할 수 있다.

**그리고 날짜를 넣기 전에 실제로 이전이 끝났는지 다시 잰다:**

```bash
dig +short NS jinazen.com          # hostcocoa.com 이면 아직 아임웹이다
curl -sI https://jinazen.com | grep -i 'server\|set-cookie'
```

## 🔴 쿠키 문구 — 지금 결정하지 않는다 (SITE-EDIT-2 [3])

소유자 확정 문안은 「호스팅 사업자가 **서비스 보안 목적으로** 쿠키를 설정할 수
있으며」다. Cloudflare 봇 관리(`__cf_bm`)를 염두에 둔 문장이다.

그런데 지금 실제로 붙는 아임웹 쿠키는 성격이 다르다.

| 쿠키 | 성격 | 만료 |
|---|---|---|
| `IMWEBVSSID` | 세션 | 세션 |
| `al=KR` | **언어 설정** | **2027-06-23 (약 10개월)** |
| `_imweb_login_state` | 로그인 상태 | 세션 |

「보안 목적」으로는 `al=KR` 을 설명하지 못한다.

**그렇다고 지금 문구를 넓히지도 않는다.** 이전이 끝나면 아임웹 쿠키는 사라지고
Cloudflare 쿠키만 남는다 — 그때는 「보안 목적」이 맞을 수 있다.
**아직 오지 않은 상태를 상상해서 문구를 고르는 것은, 시행일에서 물러선 이유와
정확히 같은 실수다.**

> **이전 후 실제로 붙는 쿠키를 다시 재고 정한다.**
>
> ```bash
> curl -sI https://jinazen.com | grep -i set-cookie
> ```
>
> 잰 결과가 Cloudflare 쿠키뿐이면 확정 문안 그대로 간다.
> 언어 설정 같은 것이 남아 있으면 그때 넓히는 안을 다시 올린다.

제6조는 **SITE-EDIT-1 에서 넣은 확정 문안 그대로 두었다. 이번에 손대지 않았다.**
